# Sigil Factory — シジル仕様書

更新日: 2026-08-22

この文書は、シジル / グリフの生成・加工・合成・描画・一致判定に関する詳細仕様をまとめる。
シジル関連の具体仕様については `GAME_DESIGN.md` の概要より本書を優先する。

---

## 1. 基本概念

### 1.1 シジルとグリフ

- **グリフ**: 工場内を流れ、加工・合成される実体
- **シジル**: 召喚獣に対応する取得済みの完成パターン
- 召喚器へ到着したグリフが、所持しているシジルと一致した場合に対応する召喚獣を召喚する
- シジルの形を知っていても、そのランでシジルを取得していなければ召喚できない

### 1.2 構造の基本式

グリフは概念上、以下の要素で表現する。

```text
GlyphSource =
  Primitive
  | RegisteredGlyph

Glyph =
  GlyphSource
  | Transform(Glyph)
  | Repeat(Glyph)
  | Combine(Glyph, Glyph, ...)
```

- `Primitive`: 基本記号
- `RegisteredGlyph`: 制作者が登録した再利用可能な意味グリフ
- `Transform`: 移動・回転・拡縮
- `Repeat`: 入力を共通原点のまわりへ等角度で反復
- `Combine`: 2〜8個のグリフの合成

`Transform` は加工中の概念モデルとして使用するが、正規化後の構造には独立ノードとして残さない。
操作履歴そのものではなく、Primitiveの最終状態、各Combine中心の最終位置、合成階層を保存する。
RegisteredGlyphはCanonicalGlyph内の新しい葉種別にはせず、登録されたPrimitive / Combine構造へ展開して扱う。

### 1.3 構造データと生産由来情報

工場内を流れる実体は、シジル一致判定に使う構造と、リリックなどの効果判定に使う生産由来情報を分離して持つ。

```text
RuntimeGlyph {
  structure: CanonicalGlyph
  productionContext: ProductionContext
}

ProductionContext {
  processingCount
  visitedNodeKinds[]
  sourceIds[]
}
```

- `structure` は最終的なPrimitive状態、各Combine中心の位置、Combine階層だけを保持する
- `productionContext` は加工回数、通過した設備種別、素材源IDなどを保持する
- 一致判定・完全重複判定・描画キャッシュキーには `productionContext` を含めない
- 「加工工程が少ない」「分配器を通過した」などのリリック判定には `productionContext` を使用する
- 設備を通過するたびに元データを変更せず、新しいContextを生成する
- Combineでは両入力の回数を合算し、設備種別と素材源IDは安定順序で重複を除いて統合する
- 召喚時に構造とContextを召喚イベントへ渡し、召喚後のグリフ実体とともに破棄する

この分離により、同じ見た目・同じ構造のグリフは常に同じシジルへ一致しながら、製造経路に意味を持つ強化も実装できる。

## 2. Primitive

### 2.1 デザイン方針

単純な `○ / △ / □` をそのまま使用するのではなく、実在するシジル・魔法陣・ルーン・錬金術図などに見られる**視覚言語を分解した独自記号**を使用する。

実在の文字・ルーンをそのまま流用するのではなく、以下のような特徴を持つ独自Primitiveを6〜8種類程度用意する。

候補となる視覚要素:

- 欠けた環
- 鉤
- 枝分かれ
- 端点を持つ形
- 短い弧
- 非対称の山形 / 牙形
- 簡潔な結晶形
- 十字・分岐を崩した形

### 2.2 Primitiveの条件

各Primitiveは以下を満たすことを優先する。

- 少ない線で構成される
- 小さく表示しても識別できる
- 他の要素と重なった際にも形を認識しやすい
- 回転後の向きを視覚的に判別できる
- 可能な限り非対称にし、回転した状態が同じ見た目になりにくい
- 単体では単純だが、組み合わせると魔術的なシジルに見える
- 基本は輪郭線主体とする

Primitive自体に装飾を詰め込みすぎず、シジル全体の複雑さは配置・回転・色・合成階層によって作る。

### 2.3 線はPrimitiveにしない

通常の接続線をPrimitiveとして用意しない。

線はグリフを合成した際に、**合成構造を示す接続として自動生成**する。

これにより、プレイヤーは線そのものを加工・位置調整する必要がなく、何をどこへ配置し、何と合成するかに集中できる。

### 2.4 Primitiveの実装方式

Primitiveの字形はPNGなどの画像アセットとして持たず、**固定ベクターパスをコード / データとして定義する方式**を基本とする。

Primitiveはランダム生成せず、字形そのものはデザイン時に固定する。コードはその固定字形を再現するために使用する。

```text
画像アセット        ×
ランダム自動生成    ×
固定Vector Path     ○
```

各Primitiveは共通のローカル座標系で定義する。初期案では `x = -1..+1`, `y = -1..+1` 程度の正規化座標を使用する。

字形を構成する描画要素は、まず以下の少数種類に限定する。

- Line
- Arc
- 必要な場合のみ Bezier / Curve

概念例:

```text
PrimitiveDefinition {
  id
  paths[]
}

Path =
  Line(start, end)
  | Arc(center, radius, startAngle, endAngle)
  | Curve(...)
```

この方式により、以下を同じ座標系・描画系で扱えるようにする。

- `Move / Rotate / Scale / Color` のTransform
- 小サイズ / 大サイズでの描画
- Primitiveの向きと形状確認
- 合成円・接続線との統一描画
- 完全重複判定に必要なPrimitive IDと最終Transformの比較

色はPrimitive画像そのものへ焼き込まず、描画時のstroke等として適用する。線幅も字形データへ固定せず、表示サイズやUIに応じて描画側で制御できるようにする。

Primitiveのデザイン変更はパス定義の変更だけで反映できる構造とし、画像の描き直し・差し替えを必要としないようにする。

## 3. Transform

基本加工は以下とする。

- `Move`
- `Rotate`
- `Scale`
- `Color`

### 3.1 離散値

加工値は自由な浮動小数点値ではなく有限段階で扱う。

初期案:

- 移動: 離散ステップ
- 回転: 現MVP工場は90°単位。Sigil Labでは中心原点を基準に1°単位
- 拡縮: 有限段階
- 色: 定義済みの色ID

具体的な移動幅・倍率・色数はプロトタイプで決定する。

### 3.2 合成済みグリフへの加工

合成後のグリフは1つのグリフとして扱い、Transformは入力されたグリフ全体へ作用する。

例:

- 合成済みグリフを着色 → 子グリフを含めた全体へ色を適用
- 合成済みグリフを回転 → 子グリフの配置・向きを含めて全体を回転
- 合成済みグリフを拡縮 → 子要素の大きさと相対位置を含めて全体を拡縮

ただし、後述する**合成構造表示用の円・接続線はゲーム上のPrimitiveではなく、構造から自動描画する表示要素**として扱う。

## 4. Combine

### 4.1 2〜8入力

CanonicalGlyphは1階層につき2〜8子を保持できる。Sigil Labの合成ノードは8入力を公開し、接続済みの入力を一度に合成する。現MVP工場の合成設備は既存レシピ互換のため2入力のままとする。

```text
Combine(A, B)
Combine(A, B, C, D, E, F, G, H)
```

同じ階層に属する3つ以上の要素は1回の合成へまとめ、不要な二項木と階層の多重化を避ける。
低位シジルを子として高位シジルへ発展させる場合は、従来どおり合成を入れ子にして階層を保持する。

```text
Combine(Combine(A, B), C)
```

これにより、同一階層の放射構造は簡潔にしつつ、意味のある合成順だけを階層として保持できる。

### 4.2 純粋関数としての合成

合成は入力グリフを変更せず、新しいグリフを返す純粋関数として扱う。

```text
result = combine(children[2..8], connectionMode)
```

- 入力グリフは所有コピーとして子へ保持する
- 入力ポート番号・接続順はCanonicalGlyphへ含めない
- 同一階層の子はCanonical serializationの安定順へ並べる
- 新規Combineの中心はグリフ共通原点 `(0, 0)` とする
- 合成後のMove / Rotate / Scaleは子PrimitiveとCombine中心の双方へ同じTransformを適用する
- 出力の分配は同じグリフを複数の下流へ渡す物流操作であり、Combine階層を増やさない

### 4.3 階層を保持する

合成時に子グリフをフラット化しない。

```text
(A + B) + C
```

と

```text
A + (B + C)
```

は異なる構造として扱う。

高位シジルは低位シジルの構造を子グリフとして保持し、その外側へ新しい加工・合成を追加して発展させる。

```text
低位シジル
  ↓
既存の低位グリフを完成
  ↓
追加加工 / 追加グリフ
  ↓
Combine
  ↓
高位シジル
```

原則として、高位シジルは前提となる低位シジルを視覚的・構造的に内包する。

### 4.4 結合方式

プレイヤーが選べる結合方式は次の3種類とする。

| 方式 | Canonical ID | 表示 | 用途 |
| --- | --- | --- | --- |
| 単純結合 | `simple` | 結合線なし | 同心配置・重ね合わせ・部品化 |
| 中心結合 | `radial` | 合成中心から各子へ放射線 | 中心と周辺の関係を示す構造 |
| 相互結合 | `pairwise` | 各子の組を互いに結ぶ線 | 多角形・網状の関係を示す構造 |

反復処理が内部で作る非表示グループ `none` はプレイヤーが選ぶCombine方式ではない。

#### 単純結合

- Primitive / 子グリフの配置だけを重ねる
- 結合線を一切生成しない
- Combine階層と中心は保持する
- 「目」「十字」のような意味を持つ中間部品を作る用途を想定する

#### 中心結合

- Combine中心から各子グリフの中心方向へ線を生成する
- 子の中心とCombine中心が同一なら、その子に対する線は生成しない
- 全子について可視線が0本になる場合は中心結合を選択できない

#### 相互結合

- 同じCombine階層に属する全子の順序なしペアを結ぶ
- 線は子グリフの可視範囲へ入る区間を描かない
- 同一直線上で重なる可視区間は1本へ正規化する
- 全ペアについて可視線が0本になる場合は相互結合を選択できない

### 4.5 結合方式の選択制約

接続済み入力が2個以上あり、結果を評価できる時点で各方式の可視線を判定する。

```text
中心結合の可視線 = 0
かつ
相互結合の可視線 = 0
  ↓
単純結合のみ選択可能
```

- 入力や上流Transformの変更で選択中方式の可視線が0本になった場合、合成ノードを単純結合へ補正する
- 可視線が0本の中心結合 / 相互結合をCanonicalGlyphとして確定させない
- 単純結合は配置にかかわらず常に選択できる
- どの方式が有効かは、完成表示と同じ接続線生成規則で判定する

### 4.6 入力順・見た目・一致

- 同じ方式・同じ階層・同じ子構造なら、入力ポート順だけが違っても同一CanonicalGlyphとする
- 単純結合 / 中心結合 / 相互結合は異なる文法なので、可視線が存在する限り別CanonicalGlyphとする
- 可視線が0本になる中心結合 / 相互結合は4.5により作成自体を許可せず、「見た目は同じだが接続方式だけ違う」完成データを増やさない
- Combine階層が異なる場合は、Primitive配置が偶然一致しても別CanonicalGlyphとする

### 4.7 登録意味グリフ

基本図形の変形・単純結合だけで意味を推測できる小さな中間グリフを登録し、上位シジルの部品として再利用する。

| 登録名 | 構造 | 読み取る意味 |
| --- | --- | --- |
| 目 | 丸 + 横長の丸 | 観測・視界 |
| 十字 | 横長の四角 + 縦長の四角 | 交差・中心 |
| 的 | 大小の同心円 | 目標・焦点 |
| 星 | 正向き三角 + 反転三角 | 星・天体 |
| 方位 | 十字 + 45°回転した十字 | 方角・全周 |

```text
Eye     = SimpleCombine(Circle, Scale(Circle, 250%, 100%))
Cross   = SimpleCombine(Scale(Square, 200%, 50%), Scale(Square, 50%, 200%))
Target  = SimpleCombine(Circle, Scale(Circle, 250%, 250%))
Star    = SimpleCombine(Triangle, Rotate(Triangle, 180°))
Compass = SimpleCombine(Cross, Rotate(Cross, 45°))
```

- 全登録グリフは結合線0本の単純結合を使用する
- 登録時も内部の子Combine構造を保持する
- 登録後は1つの意味グリフとして呼び出し、Move / Rotate / Scale / Repeat / Combineへ再入力できる
- 登録名や元グラフのノードID・配置は一致判定へ含めず、展開後のCanonicalGlyphだけを一致対象にする
- 各登録元グラフは `experiments/sigil_lab/registered/<id>.json` に保存する
- 新規登録は「名前を見なくても多くの人が同じ意味を答えられる」ものだけに限定し、解釈が割れる装飾形は追加しない

## 5. 合成構造の可視化

### 5.1 完成表示では階層円を描かない

Combine階層はCanonicalGlyphへ保持するが、自動生成した囲い円を完成シジルへ常時表示しない。
これにより、合成済みの意味グリフを別の部品として重ねても、括弧円が過剰に増えて形を隠さないようにする。

```text
(A + B) + C
```

と

```text
A + (B + C)
```

はCanonicalGlyph上では異なる階層として保持するが、完成表示の自動円だけで差を表現することはしない。

### 5.2 編集補助の階層表示

Sigil Labの「階層」表示を有効にした時だけ、編集補助として各Combine範囲を点線の真円で示す。

- 円中心は各Combineが保持する最終中心位置とする
- 円半径は子Primitive群を収めるよう描画時に算出する
- Move / Rotate / Scale後もCombine中心へ追従する
- 円は入力選択・一致判定・登録グリフの構造を変更しない
- 小型完成表示と通常の完成シジルでは初期状態を非表示とする

### 5.3 円を意味形状として使う場合

完成シジルに円を表示したい場合は、自動階層円ではなく基本Primitiveの「丸」をScale / Moveして明示的に組み込む。

- 明示的な丸は通常のPrimitiveとして加工・反復・合成できる
- 明示的な丸はCanonicalGlyphと一致判定へ含める
- 編集補助の階層円はCanonicalGlyphへ含めない

### 5.4 接続線

接続線はPrimitiveではなく、4.4の結合方式と正規化後の子配置から自動生成する。

- プレイヤーは接続線を直接移動・回転・削除しない
- 線はPrimitiveより背面へ描画する
- 単純結合は接続線を生成しない
- 中心・相互結合の可否判定と完成描画は同じ線生成結果を使用する
- 階層表示を非表示にしても接続線は結合方式の意味形状として残る

## 6. 重なり

### 6.1 基本ルール

要素同士の重なり自体は許可する。ただし、**見た目から複数要素が存在することを判別できなくなる完全重複は禁止**する。

- 同一Primitive
- 同一位置
- 同一回転
- 同一倍率
- 同一色

が揃い、完全に同じ見た目となる要素同士は同じグリフ内に存在できない。

### 6.2 許可する重なり

- サイズが異なり両方を識別できる場合
- 異なるPrimitiveで両方を識別できる場合
- 部分的な重なりで構造を読める場合

サイズ違いで重なる場合は、原則として**小さい要素を手前**に描画する。

### 6.3 描画順

プレイヤーには前面 / 背面のレイヤー操作をさせない。

描画順はシステム側で決定し、同じシジルデータから常に同じ見た目を生成する。

読みにくい重なりがプロトタイプで多発する場合は、許可条件をさらに制限する。

## 7. 正規化

### 7.1 基本方針

**見た目が同じ状態は同じデータとして扱う。**

プレイヤーの加工履歴の違いによって、見た目が同じグリフが別データになる状態を作らない。

例:

```text
Rotate(90°) → Rotate(90°)
```

と

```text
Rotate(180°)
```

は同じ最終状態として扱う。

同様に、

```text
Move(+1, 0) → Move(-1, 0)
```

は移動していない状態と同一にする。

### 7.2 最終状態を保持する

Primitiveの葉には加工履歴ではなく、最終的な状態を保持する。

概念例:

```text
PrimitiveState {
  primitiveId
  position
  rotation
  scale
  colorId
}
```

- 回転値は定義された周期内に正規化する
- 無意味な移動・回転・倍率変更は最終状態へ畳み込む
- Primitive自体を非対称寄りに設計し、回転対称による例外処理を可能な限り減らす

現MVP工場では90°回転を原点基準の整数座標変換として適用する。Sigil Labでは整数度を受け取り、全子Primitiveの位置と向きを同じ中心原点の周囲で回転し、位置を1/1000グリッドへ正規化する。
合計360°になる分割回転、相殺する移動・着色は加工履歴を残さず、同じ最終CanonicalGlyphへ正規化する。

### 7.3 Combineの正規化

同じ階層・同じ配置で、単に入力ポートへ入った順序だけが異なる場合は同一構造として扱う。

一方で、

```text
(A + B) + C
```

と

```text
A + (B + C)
```

は意味上の括弧構造が異なるため、別シジルとして保持する。編集時は任意の階層オーバーレイで差を確認できる。

### 7.4 正規形と座標系

正規化後の `CanonicalGlyph` は、Combine階層とPrimitiveの葉だけで構成する。

```text
CanonicalGlyph =
  PrimitiveLeaf(PrimitiveState)
  | CombineNode(origin, connectionMode, CanonicalGlyph[2..8])
```

- 全PrimitiveStateはグリフ共通のルート座標系で保持する
- 新規Combineの中心は `(0, 0)` とする
- Move / Rotate / Scaleは原点を基準に全子Primitiveへ再帰的に合成し、葉の最終状態へ畳み込む
- 合成済みGlyphへのMove / Rotateは、各Combineノードの最終中心位置にも再帰的に適用する
- Colorは対象以下の全子Primitiveの最終 `colorId` へ畳み込む
- Combineノードは操作履歴や回転値を持たず、描画と一致に必要な最終中心位置だけを保持する
- Combineノードは単純結合 / 中心結合 / 相互結合 / 反復内部グループの接続方式を保持し、一致判定へ含める
- 編集補助円の中心・半径と接続線は、正規化後の子Primitive群・中心・接続方式から描画時に算出する
- RegisteredGlyphの名前や登録元グラフは正規形へ残さず、展開済みのPrimitiveLeaf / CombineNode構造を使用する

Combineの2〜8入力は意味上可換とし、入力ポート番号や到着順を正規形へ含めない。各子を次の安定キーで昇順に並べる。

```text
childKey = hash(canonicalSerialize(child))
```

ハッシュ衝突時はハッシュ値だけで同一判定せず、正規化シリアライズ本体を辞書順で比較する。
正規化シリアライズでは、Primitive ID、離散位置、正規化回転、倍率段階、色ID、Combine中心位置、子構造を固定順序で出力する。Primitive ID、色ID、各子シリアライズのような可変長値は文字数を先頭へ付けた長さ付きフレームとして符号化し、値に区切り文字が含まれても異なる構造が同じ本文にならないようにする。
回転計算中の浮動小数点を正規形へ直接出力しない。位置は1/1000グリッドの整数単位へ量子化してから固定表記し、角度は0〜359の整数度、その他は離散IDまたは整数段階として出力する。

正規化処理の順序は以下で固定する。

1. Transformを葉のPrimitiveStateへ畳み込む
2. 回転・移動・倍率・色を定義済みの離散値へ正規化する
3. 各Combineの子を安定キーで並べる
4. 完全重複を検証する
5. 正規化シリアライズと構造ハッシュを生成する

一致判定では構造ハッシュを高速な事前比較に使用し、最終的には正規化シリアライズまたは構造本体を比較する。

現MVPの工場編集UIでは、選択中の術式に対応する完成シジルを小型ゴーストとして常設表示する。
ゴーストは別画像ではなくCanonicalGlyphのPrimitive状態とCombine有無から描画し、実際の一致対象と表示のずれを防ぐ。
完成見本、設備内、ライン輸送中のGlyphは共通描画器を使用し、Primitive形状、色、回転、倍率、合成外周の規則を一元化する。利用箇所は表示サイズだけを指定し、同じGlyphが画面ごとに異なる図形へ見えないようにする。
副作用なしの到着前レシピ判定は欠損候補を空バッファとして黙認せず、候補位置付きの`missing_glyph`として失敗させる。欠損候補に対して正規化・一致比較を呼ばず、イベントと廃棄数も変更しない。

召喚レシピはレシピIDとCanonicalGlyph構造の双方を一意とする。同じIDの再登録、および別IDから同一の正規化構造へ
異なる召喚結果を割り当てる登録を拒否し、受理したレシピは安定ID順に保持する。構造重複はハッシュだけでなく正規化本文で確認する。
レシピ登録時はID、召喚結果、CanonicalGlyphを所有コピーし、登録元オブジェクトの後続変更から隔離する。工場状態の複製時もレシピを再コピーし、非破壊プレビュー側の変更が実工場の一致判定へ伝播しないようにする。
登録境界ではレシピIDと召喚結果IDを必須とし、Glyphが「1個の有効なPrimitive葉」または「2〜8子のCombine」の再帰構造であることを検証する。空Glyph、平坦な複数Primitive、1子/9子以上のCombine、空Primitive/色ID、1未満の倍率段階、完全重複を持つ定義は召喚判定へ入る前に拒否する。
レシピまたはGlyph自体が欠損している場合も参照前に拒否し、候補indexと`<null>`を含む位置付き理由を返す。登録済みレジストリが外部復元後に破損している場合は、その既存位置を示して新規登録を停止し、正規化やコピーを先に行わない。
レシピモデル生成・メタデータコピーは欠損Glyphを一時的に保持できるものとし、構築途中で参照エラーにせず登録境界の共通診断へ到達させる。欠損状態を召喚判定へ登録することは引き続き禁止する。
外部復元されたCombine構造は木であることも検証し、祖先への循環参照とnull・非Glyph子を経路付きエラーとして停止保証付きで拒否する。循環を含むデータへ正規化シリアライズや深いコピーを先に実行しない。
外部復元Glyphのnull component／null childはモデル生成・診断用コピーで一時保持し、構築中に参照せず`invalid_component`／`invalid_child`として経路付き拒否する。不正要素は子からのcomponent再構築と完全重複検査では読み飛ばし、登録前構造検証より先に例外化させない。
レシピ登録判定は副作用なしの構造化診断を提供し、必須ID、Glyph構造、重複レシピID、重複CanonicalGlyphを安定優先順で返す。既存のbool登録APIはこの診断結果を使用し、拒否時にレジストリを変更しない。
MVPコンテンツはレシピ集合全体を工場構築前に同じ登録規則で順次検証し、候補index、レシピID、全拒否理由を集約する。不正定義を黙って欠落させず、開発時アサートでコンテンツ位置を示して停止する。

## 8. シジル一致判定

召喚器での一致判定は描画画像ではなく、正規化された構造データで行う。

一致条件に含める:

- Primitiveの種類
- 位置
- 回転
- 倍率
- 色
- Combineの階層構造

一致条件に直接含めない:

- 描画上の線幅
- 発光表現
- パーティクル
- アニメーション
- 編集補助円の描画サイズそのもの
- 接続線の描画形状そのもの

編集補助円は一致に影響しない。接続線の線幅・端点の描画調整は一致へ含めないが、接続方式IDはCombineNodeの一部として一致へ含める。

部分一致は認めず、入力グリフ全体が取得済みシジル全体と一致した場合のみ召喚する。
一致判定API自体も欠損した入力／シジル定義と、正規化を危険にする不正component・child・循環を含むGlyph構造を正規化前に検証する。不正時は入力側か定義側かと構造経路を含む不一致診断を返し、参照エラーや無限再帰にしない。安全に比較可能な複数部品などは従来の不足・余分・属性差分へ流し、完全重複も既存のプレイヤー向け診断を優先する。

## 9. シジル文法

シジルは暗記用のランダムな図柄ではなく、プレイヤーが未知の上位シジルを見た際に、ある程度性質や必要工程を予測できる規則性を持たせる。

初期方針:

- Primitive → 召喚獣の性質・役割・系統を示す主要情報
- Color → 属性を示す主要情報
- Combine hierarchy → 派生・進化・能力構成を示す主要情報
- Scale → 規模・大型化などの補助情報
- Position / Rotation → 挙動・方向性・派生を示す補助情報

文法を増やしすぎず、まずは **Primitive / Color / Combine hierarchy** を強い規則として設計し、その他は補助的に扱う。

最終的な意味対応は、実際に複数のシジルツリーを設計してから確定する。

## 10. 低位・高位シジルと進化

### 10.1 基本方針

高位シジルは、低位シジルを応用して作れる構造にする。

- 前提低位シジルを所持していない場合、その高位シジルは報酬候補に出現しない
- 基本的には高位シジルを製造できるなら高位の方が強いゲームバランスとする
- 高位ほど追加素材・加工・合成などを要求し、より複雑な工場ラインが必要になる
- 低位を主力にする例外はリリックなどのローグライト強化によって作る

高位化は単に末尾へ工程を1つ追加するだけにならないよう、別素材源との合成や配置変更など、工場の再設計を要求する余地を持たせる。

### 10.2 進化ポイント

シジル進化の必須条件を、そのシジル固有の召喚数にはしない。

ラン中に**共通の進化ポイント**を獲得し、プレイヤーが任意の所持シジルへ割り振れる方式を基本とする。

```text
ステージクリア / イベント / その他報酬
  ↓
共通進化ポイント獲得
  ↓
所持シジルから育てたいものを選択
  ↓
一定値に到達
  ↓
上位シジル候補から1つ取得
```

これにより、ラン中盤・後半で新しく取得したシジルも、過去の召喚数が0であることを理由に進化が遅れすぎないようにする。

進化ポイントは、未使用のまま保持して後から取得したシジルへ投入できるようにしてよい。

### 10.3 使用ボーナス

実際に使用したシジルには、共通進化ポイントとは別に**追加の進化ボーナス**を与える。

例:

```text
対象シジルを一定数召喚
  ↓
そのシジルへ追加進化ポイント
```

これにより、

- 新規シジルも共通ポイントで即座に育成できる
- 実際に使い続けたシジルは自然に進化が早まる
- 「進化させるためだけに弱いシジルを大量召喚する」ことを必須にしない

という状態を狙う。

召喚数は進化の必須条件ではなく、**使い込んだシジルを優遇する補助条件**として扱う。

具体的なボーナス量・何体ごとに付与するかはバランス調整で決定する。

### 10.4 新規取得シジルのキャッチアップ

後半で入手したシジルが、既存シジルに対して育成面で大きく不利にならないようキャッチアップを持たせる。

第一候補は、共通進化ポイントを貯めて新規取得シジルへ即時投入できる仕組みとする。

必要であれば追加で、以下のいずれかを検討する。

- ラン進行度に応じて初回進化までの必要ポイントを軽減する
- 新規取得時に一定量の進化ポイントを付与する
- 同系統シジルの進化実績の一部を共有する

ただし基礎リソースや進行システムを増やしすぎないため、まずは**共通進化ポイントのみで十分なキャッチアップが成立するか**を検証する。

### 10.5 進化候補

進化条件を満たした際は、前提シジルから派生する上位シジル候補を複数提示し、その中から1つを取得する方式を基本とする。

初期案は**2択**とする。

- 前提シジルを所持していない上位シジルは候補に出さない
- 現在所持している素材・加工器で製造可能な候補を優先する
- 進化先によって召喚獣の役割だけでなく、要求される工場構造も変化させる
- 選ばなかった派生を同一ラン中に再取得できるかは未確定とする

### 10.6 進化取得UI

上位シジル取得時は完成形だけでなく、**前提シジルから何が追加・変更されたかを差分で表示**する。

```text
前提シジル
  ↓
追加Primitive / Transform / Combine を強調表示
  ↓
進化後シジル
```

これによりプレイヤーが、

- 既存工場のどこをそのまま流用できるか
- どの加工器・素材源を追加する必要があるか
- どこに拡張余地が必要か

を進化選択時点で予測できるようにする。

## 11. アート上の方針

- 黒〜非常に暗い背景
- 白い輪郭線を基本とする
- 接続線と任意表示の階層円も同じ魔導線の視覚言語で統一する
- 属性など、意味を持つ箇所に限定して色を使用する
- Primitive単体は簡潔にし、複雑さは組み合わせによって生み出す
- 高位シジルは低位シジルの構造が内側に残り、その外側へ術式が発展していくように見せる
- 実在のシジルそのものをコピーせず、歴史的な魔術図像の視覚要素を抽出して独自デザインとする

# Sigil Factory — シジル視覚仕様書

更新日: 2026-08-22

この文書は、シジル、グリフ、素材表示、召喚器、およびそれらに関連する視覚表現の基準をまとめる。
シジルの構造・一致判定・進化などの論理仕様は `SIGIL_SPEC.md` を参照する。
視覚表現については本書を優先する。
現在の工場プロトタイプはSigil LabのGraphEdit表示を起点とし、採用機能と表示サイズは `FACTORY_PROTOTYPE.md` を優先する。召喚器、輸送アニメーション、専用ノード外形に関する記述は後段のアート目標であり、現行値グラフの必須条件ではない。

現時点では、特定の基準画像を正式なアートリファレンスとして採用しない。
Codex等で実装・改善する場合は、画像の雰囲気を推測して再現するのではなく、以下の文章仕様を基準とする。

---

## 1. 視覚上の目的

シジルは単なるレシピIDやノードエディタ上のデータではなく、**このゲームの中心的な視覚モチーフ**として扱う。

プレイヤーが画面を見たとき、テキストを読まなくても以下を認識できる状態を目指す。

- どのPrimitiveを扱っているか
- 現在流れているグリフがどのような形か
- どのシジルを目標としているか
- 合成によってどの構造が作られているか
- 完成ノードと通常の加工ノードを区別できること

UI文字で説明するのではなく、**実際の記号・構造・流れを見せることを優先する**。

---

## 2. 基本アート方向

全体の基調は **黒い魔術書 / 魔導回路** とする。

- 背景は黒〜非常に暗い色
- シジルとグリフは細い輪郭線主体
- 白〜淡い発光色を基本とする
- 色は属性や状態など、ゲーム上意味を持つ場合に限定する
- 魔法陣、錬金術図、星図、電子回路の中間のような印象を目指す
- 過剰な装飾、読めない細密模様、意味のない文字列は追加しない
- 実在の魔術記号やルーンをそのままコピーしない

「派手なネオンSF UI」そのものを目標にはしない。
発光は補助表現であり、**形状そのものの可読性を最優先**する。

---

## 3. 視覚階層

完成シジル内部では、以下の順に視覚的な強さを付ける。

```text
Primitive
  > Connection Line
  > Hierarchy Overlay（編集時のみ）
```

### 3.1 Primitive

最も強く見せる。

- シジルを構成する意味のある実体
- 他の構造線より明確に認識できる線幅・明度を持たせる
- 小サイズでも種類と向きが判別できることを優先する

### 3.2 Connection Line

Primitiveより弱く表示する。

- 合成構造を読み取るための補助線
- Primitiveより細く、明度も抑える
- 接続線が増えてもシジル本体を覆わないようにする

線は結合方式に意味がある場合だけ表示する。単純結合では表示せず、中心結合は共通原点から各子へ、相互結合は各子の可視範囲間を結ぶ。

### 3.3 Hierarchy Overlay

合成階層を示す真円は、Sigil Labの「階層」切替を有効にした編集時だけ点線で表示する。

- 完成表示では初期状態を非表示とする
- PrimitiveとConnection Lineより弱くする
- Move / Rotate / Scale後のCombine中心へ追従する
- 円そのものを完成シジルの装飾や一致対象にしない
- 完成形に円が必要な場合は基本Primitiveの丸を明示的に使う

具体的な線幅・透明度は表示サイズに応じて調整するが、この相対関係は維持する。

---

## 4. Primitive表示

素材やグリフを、名称だけのテキストとして表示しない。

例えば `丸` を扱う場合でも、UI上では実際のPrimitive字形を主要表示とし、名称は補助ラベルとする。

```text
[ Primitive記号 ]
	丸
```

Primitiveの字形は `SIGIL_SPEC.md` の通り、固定ベクターパスから描画する。

- PNG等の固定画像を主データにしない
- ランダムな魔法陣を生成しない
- Primitiveごとに同じベクター定義を、素材ノード、ライン上グリフ、完成見本、召喚判定表示で再利用する

これにより、同じPrimitiveがUIごとに異なる見た目になることを防ぐ。

---

## 5. 完成シジルの表示

完成シジルは小さなアイコンや文字だけで済ませず、**プレイヤーが形を読み取れる十分なサイズで表示する**。

現行プロトタイプでは自由構築した完成候補を常時確認できるようにする。将来レシピを選択して製造する段階では、現在目標としているシジルも同じ描画器で併記する。

表示候補:

- 工場領域内の目標シジル表示
- 選択中シジルの詳細プレビュー
- 工程差分表示
- 召喚器へ到着するグリフとの比較表示

完成見本はCanonicalGlyphから実際に描画し、別途用意したイラストへ置き換えない。

これにより、ゲーム内で作る形と見本が一致することを保証する。

現行Sigil Labの完成プレビューは310pxを基準とし、同じCanonicalGlyphを104px / 56px / 36pxでも同時確認する。工場プロトタイプへ移植する際も、各ノードの中間プレビュー、完成プレビュー、縮小確認で同じ共通描画器を使う。
完成候補を作れない無効・未配線状態は空枠で示し、古い候補を成功例のように残さない。完成工程の答え、必要ノード、正解経路は常時表示しない。
将来、目標レシピとの比較を追加する場合は、目標Glyphと完成候補を並べ、形だけでも一致・不一致を区別できる表示にする。ただし現在の工場プロトタイプは自由構築とJSON書き出しを先に検証し、レシピ一致UIを必須にしない。

---

## 6. グリフの可視化

ライン上を流れる対象は単なる丸・点・箱ではなく、可能な範囲で**現在のグリフ形状そのもの**を表示する。

少なくとも以下を識別できることを目指す。

- Primitiveの種類
- 回転
- 横縦倍率
- 反復数
- おおまかな合成状態

小さすぎて完全な構造表示が不可能な場合は簡略表示してよいが、選択・ホバー・拡大時にはCanonicalGlyphの実形状を確認できるようにする。

工場プロトタイプでは各ノード内に純粋関数の出力Glyphを表示し、完成ノードへ接続された結果を大判表示する。固定tick導入後に設備・輸送ラインへホバーする場合も同じ描画器を使い、表示対象は所有コピーとしてシミュレーション状態を変更しない。

---

## 7. 素材ノード

素材源 / 素材ノードは、汎用の矩形ボックスへ名称だけを表示する状態を完成形としない。

- Primitive字形を主要表示とする
- 名前は補助情報とする
- 入出力ポートは `FACTORY_SPEC.md` の方向非依存ポート仕様を使用する
- 他の加工器と区別しやすい専用のシルエットまたは内部記号を持たせてよい

ただし、ノード外枠自体を複雑にしすぎず、内部のPrimitiveが最も読みやすい状態を優先する。

---

## 8. 完成ノードと将来の召喚器

現行プロトタイプでは完成ノードを1基だけ置き、どの中間ノードからでも `◎` の完成操作で安全に接続先を切り替えられるようにする。
完成ノードは通常の加工ノードとタイトル色・出力ポートの有無・大判プレビューで区別する。値グラフの検証中は、GraphNodeの矩形外形を仮UIとして使用してよい。

将来、完成ノードを召喚器へ置き換える場合は、通常の加工ノードと同じ矩形ボックスを完成形としない。

中央に置かれる工場の中心設備として、**円形 / 魔法陣型の専用シルエット**を基本とする。

- 複数ラインが周囲から接続できる
- 入力方向に依存しない
- 接続されたグリフが中央へ吸い込まれていく印象を持たせる
- 合致時には短い発光・リング反応などで召喚成功を示してよい
- 常時過剰に発光させず、通常状態と召喚成功状態の差を残す

召喚器そのものに複雑な固定魔法陣を描き込みすぎない。
シジルの完成形と視覚的に競合しないことを優先する。

---

## 9. 工場ライン

工場ラインは単なるUI上の破線ではなく、**グリフを輸送する魔力導線**として表現する。

ただし、装飾しすぎて配線構造が読めなくならないようにする。

- 基本形状は `FACTORY_SPEC.md` の通りノード間の直線
- 流れる方向を小さな方向マーカーで示す
- 実際にグリフが移動することで流向を補強する
- 発光は控えめにし、グリフの方をラインより目立たせる
- 接続可能 / 選択中 / エラーなどの操作状態は一時的な強調で表現する

通常状態のラインが、シジルやグリフより視覚的に強くならないようにする。

---

## 10. ノード全体の方向性

工場ノードは一般的なWeb系ノードエディタの見た目をそのまま完成形にしない。

避けたい状態:

```text
┌─────────┐
│ 丸       │
└─────────┘
```

目指す状態は、形状・内部記号・ポートを見るだけで役割が把握できる**小型の魔導装置**である。

工場プロトタイプは現行Sigil LabのGraphNodeをそのまま機能基準にし、素材 / 登録 / 移動 / 回転 / 変形 / 反復 / 合成 / 完成をタイトルと実Glyphプレビューで区別する。六角形・角落とし・二重円などの専用外形は、値グラフの操作が成立した後のアート段階で比較する。
ノード追加UIも盤面上の視覚言語を再利用する。基本素材は丸・三角・四角の実形状、登録素材は登録済みGlyph、加工は方向・角度・横縦倍率・反復・結合方式を示す記号を主表示とし、短い名称を補助ラベルにする。着色器と分配器の記号は用意しない。

ただし、すべてのノードへ大量の装飾を追加するのではなく、以下を優先する。

1. 内部の記号
2. 入出力
3. ノード種別
4. 装飾

装飾は最後に追加する。

---

## 11. UI文字との関係

プロトタイプ段階では説明用テキストを多く表示してよいが、完成形では徐々に図形情報へ置き換える。

例えば以下はテキストだけに依存しない。

- 素材種類
- 加工種類
- 目標シジル
- 現在グリフ
- 入力 / 出力方向
- 合成構造

テキストは、図形を理解した後の確認・補助情報として使用する。

---

## 12. 実装・改善時の優先順位

見た目を改善する場合は、以下の順で進める。

1. Primitiveそのものを正しく・読みやすく表示する
2. 完成シジルを十分なサイズで表示する
3. ライン上のグリフを実形状で見せる
4. 完成ノードを通常ノードと明確に区別する
5. 素材ノード・加工器・合成器の視覚差を整理する
6. Connection Line / Hierarchy Overlayの視覚階層を調整する
7. 発光・パーティクル・装飾を追加する

**装飾を先に増やして、シジル自体が読みにくい状態にはしない。**

---

## 13. Codex実装時のルール

Codex等の実装エージェントは、シジル表示を変更する前に最低限以下を確認する。

- `docs/SIGIL_SPEC.md`
- `docs/SIGIL_VISUAL_SPEC.md`
- `docs/FACTORY_SPEC.md`
- `docs/FACTORY_PROTOTYPE.md`

見た目改善を依頼された場合でも、現在の仮UIへ単純に装飾を追加するだけで完了としない。

特に以下を守る。

- Primitiveは実ベクター形状を描画する
- シジル構造と表示が乖離しない
- CanonicalGlyphを表示のSingle Source of Truthとする
- 完成表示では自動階層円を描かず、必要な円は基本Primitiveとして構成する
- Combine階層の真円は任意の編集オーバーレイ、接続線は結合方式の意味形状として扱う
- 視覚階層 `Primitive > Connection Line > Hierarchy Overlay` を維持する
- ゲームルールに存在しない飾り線・文字・記号をシジル内部へ追加しない
- アート改善のために一致判定データを変更しない
- 発光や線幅などの純粋な描画パラメータは一致判定へ含めない

---

## 14. 基準画像について

現時点では正式な基準画像は設定しない。

画像生成による参考案を作成することはできるが、採用が明示されていない画像をCodexが実装基準として扱わないこと。

将来、正式な基準画像を採用する場合も、画像をそのまま再現するのではなく、まず以下へ分解して仕様化する。

- Primitive字形
- 線幅
- 余白
- Connection Line
- Hierarchy Overlay
- 発光
- 状態色
- UI内での表示サイズ

画像と文章仕様が矛盾する場合は、文章仕様を優先する。

## 15. 反復改善ループ

シジルの視覚改善は、一度の大規模改修で完成させようとせず、**短い比較ループを繰り返して改善する**。

基本ループ:

```text
現状画面を確認
  ↓
最も大きい視覚上の問題を1〜2件だけ選ぶ
  ↓
原因を構造 / レイアウト / 線 / 色 / 装飾に分解する
  ↓
最小限の修正を実装
  ↓
同じ条件でスクリーンショットを取得
  ↓
修正前後を比較
  ↓
改善していれば残す / 悪化していれば戻す
  ↓
次の1〜2件へ
```

### 15.1 1ループで変更する範囲

原則として、1回の改善で複数の要因を同時に大きく変更しない。

良い例:

- Primitiveの線幅とサイズだけを調整する
- 完成シジルの表示サイズと配置だけを変更する
- 完成ノードの状態差を外形とポートで明確にする
- Connection Lineだけを弱くする

避けたい例:

- Primitive、背景、全ノード、ライン、発光、レイアウトを一度に全面変更する

一度に多く変えると、何が改善・悪化の原因だったか判断できなくなる。

### 15.2 評価順序

各ループでは以下の順で評価する。

1. **読めるか** — Primitive、回転、倍率、反復数、結合方式を識別できるか
2. **主役が分かるか** — シジル / グリフがUI枠や文字より先に目へ入るか
3. **構造が分かるか** — Primitive、Connection Line、任意のHierarchy Overlayの関係を追えるか
4. **工場内で一貫しているか** — 素材ノード、ライン上、完成見本で同じ字形に見えるか
5. **魔術的に見えるか** — 上記を満たした上で世界観に合っているか
6. **装飾が邪魔していないか** — 発光や枠が情報より強くなっていないか

「格好いいか」だけを最初の評価基準にしない。

### 15.3 比較条件を固定する

修正前後の比較では、可能な限り同じ状態を使う。

- 同じシジル
- 同じ工場構成
- 同じズーム
- 同じ画面サイズ
- 同じ選択状態
- 同じグラフと完成接続状態

これにより、実装変更そのものの効果を判断しやすくする。

### 15.4 スクリーンショットで確認する対象

最低限、以下の4種類を確認する。

1. 丸・三角・四角の基本素材と登録意味グリフ
2. 2〜8入力Combineと2階層以上の完成シジル
3. Repeatと直接分岐を含むグラフ
4. 同じ完成Glyphの310px / 104px / 56px / 36px表示

単体プレビューだけ綺麗でも、実ゲームサイズで読めなければ不合格とする。

### 15.5 Codexの改善単位

Codexへ視覚改善を依頼する場合は、各ループで以下を実行させる。

1. `SIGIL_SPEC.md`、`SIGIL_VISUAL_SPEC.md`、`FACTORY_SPEC.md` を確認する
2. 現在の実装と画面を確認する
3. 現時点で最も影響の大きい問題を1〜2件挙げる
4. その問題だけを修正する
5. 既存の論理仕様・一致判定を変更していないことを確認する
6. 可能なら同一条件のスクリーンショットで比較する
7. 次の改善候補を列挙して終了する

Codex自身に無制限な全面リデザインをさせず、**小さい修正と確認を繰り返すこと**を基本とする。

### 15.6 最初の改善対象

現在の工場プロトタイプでは、最初の改善ループを以下の順で進める。

1. 素材ノードにPrimitive実形状を明確に表示する
2. 完成シジルを十分な大きさで読めるようにする
3. 中間ノードと完成ノードの実Glyphを同じ描画器で表示する
4. 移動・回転・変形・反復・合成の設定を図形で読めるようにする
5. Primitive / Connection Line / Hierarchy Overlayの視覚階層を調整する
6. ノード外形とポートを `FACTORY_SPEC.md` の方向非依存デザインへ寄せる
7. 最後に発光・装飾・演出を調整する

この順序より先に背景装飾や大規模なUIフレーム変更へ時間を使わない。

## 16. 未確定事項

今後の実装・画面確認を通して決める。

- Primitiveの最終字形
- Primitive / Connection Line / Hierarchy Overlayの具体的な線幅比
- 発光量
- 完成シジルの標準表示サイズ
- ライン上グリフをどこまで簡略化するか
- 完成ノードと将来の召喚器の最終シルエット
- 各加工器 / 合成器の最終ノードデザイン
- 任意表示する階層円と子要素の余白量
- 接続線がPrimitive・円と交差する場合の具体的な処理
